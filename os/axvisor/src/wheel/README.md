# Wheel Port

This directory is the Axvisor port of `/home/ajax/Downloads/lunzu/wheel/ESP32/WBR_Control`.

The original ESP32 code ran an Arduino loop at `dt = 0.008 s` and mixed these responsibilities:

- Serial/Wi-Fi command handling.
- MPU6050 I2C reads and coordinate conversion.
- Lingkong motor UART transactions.
- LU9685 hip-servo writes.
- EKF state estimation and LQR control.
- Telemetry logging.

The Axvisor RT executor is cooperative, so this port keeps blocking I/O out of the control core. The current stage contains:

- WBR control constants and LQR gain table.
- 8 ms wheel-controller step orchestration.
- IMU raw-to-body-frame conversion.
- Hip-servo angle mapping.
- Lingkong `0xA1` torque-command and `0x9C` state-frame helpers.
- The `POL` height/hip kinematics, CoM/inertia calculation, and core dynamics prediction.
- The EKF state estimator.
- An `rt-wheel` hardware path under `hardware.rs` that owns its own MPU6050, UART7 servo, and UART3/UART6 motor adapters.

The ESP32 controller used `dt = 0.008 s`; this port keeps that period. The `POL` prediction currently uses the same mass matrix, nonlinear terms, inverse kinematics, and observation model, but the state-transition Jacobian is generated by finite differences rather than directly hand-porting the long analytic Jacobian. Validate against captured ESP32 logs before relying on actuator output.

`rt-wheel` deliberately does not enable the standalone `rt-mpu6050`, `rt-uart`, or `rt-motor` demo tasks. Those tests remain available through their original board configs. Use `configs/board/orangepi-5-plus-rt-sd-wheel.toml` to build only the 8 ms wheel-control task.

The wheel hardware adapters use short polling budgets and fail the current cycle instead of waiting for the old diagnostic-scale timeouts. On a failed control cycle the task sends zero motor torque and waits for the next 8 ms period.
